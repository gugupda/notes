# 迭代开发版本与分支的关系

软件版本（如 v1.0、v1.1、v2.0 这类可独立运行的发布版本）并不应该对应 GitHub 上的分支，二者是不同层面的概念，对应关系和用途完全不同**。下面我们详细拆解这个问题，并给出更合理的版本管理方案：

### 一、先明确：分支 vs 软件版本（核心概念区分）

#### 1. GitHub 分支（Branch）的核心定位

分支的本质是**用于并行开发的 “临时开发线”**，目的是隔离不同的开发任务（如功能开发、bug 修复），避免互相干扰主分支的稳定代码。它是**开发过程中的中间载体**，不是最终的版本交付物，通常会随着任务完成被合并（merge）后删除（除核心分支外）。

比如：你要开发 v1.1 版本的 “用户评论功能”，会创建 `feat-comment` 分支，开发完成后合并到主分支，随后这个 `feat-comment` 分支就可以删除了 —— 它只是开发该功能的临时容器，不是 v1.1 版本本身。

#### 2. 软件版本（如 v1.0、v1.1、v2.0）的核心定位

软件版本是**可独立运行、可交付给用户 / 测试的最终产物**，是**开发成果的 “快照标记”**，对应某一时间点仓库中稳定、完整的代码状态，用于回溯、发布和归档。

比如 v1.0 对应 “基础功能完整可用” 的代码快照，v1.1 对应 “基础功能 + 用户评论功能” 的代码快照，这些快照是固定不变的，便于后续快速定位某个版本的代码。

### 二、软件版本在 GitHub 上的正确对应物：Git 标签（Tag）

**与软件版本（v1.0、v1.1 等）直接对应的，是 Git 标签（Tag），而非分支**。

标签的本质是**指向特定提交（commit）的 “永久静态标记”**，一旦创建就不会随代码变更而移动，完美匹配软件版本 “固定快照” 的特性，是标记发布版本的标准方案。

#### 标签的核心操作（命令行）

```bash
# 1. 为当前代码状态创建「附注标签」（推荐，包含版本描述、作者等信息，适合发布版本）
# 对应软件版本 v1.0，描述信息明确版本特性
git tag -a v1.0 -m "v1.0 基础版本：支持用户注册、登录和基础数据查询"

# 2. 查看所有已创建的版本标签（对应所有软件版本）
git tag

# 3. 将标签推送到 GitHub 远程仓库（便于团队共享和归档）
git push origin v1.0
# 若有多个标签需批量推送
git push origin --tags

# 4. 后续回溯某个软件版本（如需要查看/修复 v1.0 版本的问题）
git checkout v1.0

# 5. 删除无用标签（若版本未发布需废弃）
# 本地删除
git tag -d v1.0
# 远程删除
git push origin --delete v1.0
```

在 GitHub 网页端，标签会自动关联 “发布（Release）” 功能，你可以基于标签创建正式的版本发布（填写更新日志、上传安装包等），方便用户下载和查看版本变更。

### 三、迭代开发中，分支的正确使用方式（核心分支模型推荐）

虽然版本不对应分支，但分支是支撑迭代开发的核心，推荐采用简洁高效的分支模型（适配你的迭代开发场景），核心分支 + 临时分支搭配使用：

#### 1. 核心长期分支（永久保留，不删除）

这类分支承载稳定代码，是迭代开发的基础，通常包含 2 个：

- `main` / `master` 分支：**主分支，存放始终可发布的稳定代码**，所有最终合并的代码都要进入该分支，对应 “最新正式版本” 的代码状态（如 v2.0 发布后，`main` 分支就是 v2.0 的代码）。
- `develop` 分支（可选，适合中大型项目 / 团队）：**开发分支，存放迭代中的最新开发代码**，作为各功能分支的合并目标，对应 “下一个版本的待测试代码”（如正在开发 v2.1，`develop` 分支就是 v2.1 的开发中的代码）。

#### 2. 临时开发分支（任务完成后合并删除，按需创建）

这类分支对应具体的迭代任务，支撑版本的逐步扩展，常见类型：

- `feat-xxx`：功能分支（如 `feat-user-comment` 对应 v1.1 的评论功能）。
- `fix-xxx`：bug 修复分支（如 `fix-login-error` 对应 v1.0.1 的登录 bug 修复）。
- `release-xxx`：版本发布准备分支（如 `release-v1.1`，用于集中测试 v1.1 版本的所有功能，修复小问题，不新增功能，测试通过后合并到主分支并打标签）。

#### 3. 迭代开发的分支流转流程（以 v1.0 → v1.1 → v2.0 为例）

1. **开发 v1.0 基础版本**：
   - 基于 `main` 分支创建临时功能分支（如 `feat-base-user`、`feat-base-data`）。
   - 各功能分支开发完成后，合并到 `main` 分支。
   - 在 `main` 分支的稳定代码上，创建标签 `v1.0`，标记 v1.0 软件版本（可在 GitHub 上发布该版本）。
2. **迭代开发 v1.1 版本（新增评论功能）**：
   - 基于 `main` 分支（v1.0 代码）创建 `feat-comment` 功能分支。
   - 开发完成后，合并到 `main` 分支，删除 `feat-comment` 分支。
   - 在合并后的稳定代码上，创建标签 `v1.1`，标记 v1.1 软件版本并发布。
3. **迭代开发 v2.0 版本（重大功能升级）**：
   - 基于 `main` 分支（v1.1 代码）创建多个功能分支（如 `feat-payment`、`feat-report`）。
   - 所有功能开发完成后，合并到 `main` 分支，删除对应临时分支。
   - 创建标签 `v2.0`，标记 v2.0 软件版本并发布。
4. **紧急修复某个版本的 bug（如 v1.0 登录 bug）**：
   - 基于 `v1.0` 标签创建修复分支 `fix-login-v1.0`。
   - 修复完成后，合并到 `main` 分支，创建标签 `v1.0.1`（补丁版本）并发布。

### 四、补充：特殊场景下的 “版本分支”（仅例外情况）

只有一种特殊场景会让 “版本” 对应 “长期分支”——**当某个旧版本需要持续维护（多次发布补丁），而新版本正在并行开发时**。

比如：你已经发布 v2.0 并继续开发 v2.1，但 v1.0 作为稳定版仍有大量用户使用，需要持续修复 bug（如发布 v1.0.1、v1.0.2、v1.0.3）。此时可以创建 `release-v1.0` 长期分支（基于 v1.0 标签），后续所有 v1.0 系列的补丁修复都在该分支上进行，修复后在该分支上打 `v1.0.1`、`v1.0.2` 标签。

这种情况下，`release-v1.0` 是 “版本专属维护分支”，但它的核心目的仍是支撑该版本的后续补丁开发，而非 “版本本身”—— 版本本身依然由标签标记，分支只是该版本的维护载体。

### 总结

1. **核心结论**：软件版本（v1.0、v1.1 等）≠ GitHub 分支，二者用途不同，版本对应 Git 标签（Tag），分支对应并行开发线。
2. **标签的价值**：静态快照、永久标记，完美匹配软件版本的可回溯、可交付特性，是版本标记的标准方案。
3. **分支的价值**：隔离开发任务、保障主分支稳定，采用 “核心长期分支 + 临时任务分支” 的模式，支撑迭代开发流程。
4. **例外场景**：仅当旧版本需要持续维护补丁时，才创建该版本的长期维护分支，版本本身仍由标签标记。
